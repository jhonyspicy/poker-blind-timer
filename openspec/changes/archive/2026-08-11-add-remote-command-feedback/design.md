## Context

リモコンの `sendCommand`(`src/pages/remote/RemotePage.tsx`)は `void channel.publish(...)` で fire-and-forget にコマンドを送っており、送信の成否を一切参照していない。サイネージはコマンドを適用してセッションが変化すると状態スナップショットを配信し返すが、リモコン側はそれを送信したコマンドと対応付けていない。

そのため利用者からは「押したのに何も起きていないように見える」「失敗しても気づけない」という状態になっている(Issue #17)。ワンオペ運営では、ボタンを押した直後にディーラー業務へ移るため、失敗が視界から消えると取り返しがつかない。

前提となる既存の作り:

- コマンドにはリモコンが生成する一意な `requestId` が付いており、サイネージは処理済み `requestId` を無視して重複適用を防いでいる(`useSignageController.applyCommand`)
- 切断時には猶予 1.5 秒を置いてから操作をブロックするモーダルを出す仕組みが既にある(`DISCONNECT_MODAL_DELAY_MS`)
- 各タブ(ControlTab / StructureTab / HistoryTab)は `sendCommand: (input) => void` を受け取るだけで、送信状態を持っていない

## Goals / Non-Goals

**Goals:**

- ボタンを押したことが手元で必ず分かる(押下 → 完了までのフィードバックが途切れない)
- 応答待ちの間に同じ操作を重ねて送れない
- 送信に失敗したとき、利用者が別作業へ移っていても気づける
- 通常の高速なラウンドトリップで画面がちらつかない
- 既存タブコンポーネントの改修を最小に抑える

**Non-Goals:**

- 送信キューやオフライン時のコマンド蓄積(切断中は既存の切断モーダルで操作を止める方針を維持する)
- コマンドごとの個別 UI(ボタン単位のスピナー表示など)。まずは画面全体で一貫した挙動にする
- サイネージ側での適用結果(採用 / 拒否)の詳細な返却。`STRUCTURE_UPDATE` の競合検出は既存のスナップショット照合を継続して使う

## Decisions

### D1: 確認はサイネージからの ACK で行う(publish 完了では不十分)

`channel.publish()` の Promise 解決は「Ably のサーバーに受理された」ことしか示さず、サイネージが落ちていても成功になる。運営者が知りたいのは「サイネージに反映されたか」なので、サイネージがコマンドを処理した時点で `requestId` を返す ACK メッセージを新設する。

**代替案**: 状態スナップショットの再受信を ACK の代わりにする。しかしセッションが変化しないコマンド(no-op の `PAUSE`、演出待ちの `START`)ではスナップショットが配信されないため、成功を取りこぼす。専用の ACK が確実。

### D2: ACK は `{ requestId, status }` の 1 メッセージ

- `status: 'accepted'` — サイネージがコマンドを受理した(処理済み `requestId` の再送も accepted を返す)
- `status: 'rejected'` — 優勝確定後などでコマンドを受け付けない状態だった

`rejected` は「届いたが受け付けられなかった」ことを示し、通信失敗と区別して案内できる。`STRUCTURE_UPDATE` の内容的な拒否は既存のスナップショット照合に任せ、ACK では `accepted` を返す(編集画面の競合表示は現状のまま動く)。

サイネージは ACK を早期リターン経路も含めてすべてのコマンドに対して返す。返さない経路が残ると、リモコン側でタイムアウト警告が誤発生するため。

### D3: 再送は同じ `requestId` を使い回す

失敗警告からの再送で新しい `requestId` を振ると、ACK だけが失われた(コマンド自体は届いていた)ケースで二重適用になる。既存の重複排除がそのまま効くよう、再送は同一 `requestId` で送る。

### D4: 入力ブロックは即時、「送信中」表示は遅延

送信開始と同時に画面全体を覆うオーバーレイを描画して入力をブロックし、視覚的な「送信中」表示は 300ms 経過後にだけ出す。通常のラウンドトリップは数百 ms 未満で終わるため、毎回モーダルが点滅するのを避けつつ、連打は最初のタップから防げる。切断モーダルの猶予(`DISCONNECT_MODAL_DELAY_MS`)と同じ考え方。

**代替案**: 押下と同時にモーダルを出す。確実だが、エントリー連続記録などのテンポの良い操作で画面が毎回フラッシュして煩わしい。

### D5: 送信状態は RemotePage に集約し、タブの props は変えない

オーバーレイで画面全体の入力を止めるため、各ボタンを `disabled` にする改修は不要。`sendCommand` のシグネチャ(`(input) => void`)も維持でき、ControlTab / StructureTab / HistoryTab に変更を入れずに済む。

同時に処理する送信は 1 件のみ(single-flight)。オーバーレイが入力を止めているため、2 件目が発生する経路は基本的にない。

### D6: 失敗は自動で消えない警告、成功は短時間の控えめな表示

- 失敗(5 秒経っても ACK が来ない / publish が reject / `rejected` を受信): 明示的に閉じるまで残るモーダル。「再送」と「閉じる」を提供する。持ち場を離れても後から気づけるようにするための中心的な要求
- 成功: 約 1 秒で自動的に消える控えめな完了表示。「押したことが分かる」ための最小限のフィードバック

タイムアウトは 5 秒とする。Ably のラウンドトリップに対して十分長く、かつ運営者が次の操作へ移る前に判定が出る長さ。

### D7: 終了・切断との優先順位

- `finished` のスナップショットを受信したら、待機中の送信状態は破棄する(接続を閉じるため ACK は来ない。終了は失敗ではないので警告を出さない)
- 失敗警告と切断モーダルが同時に成立し得る。失敗警告を前面に出す(利用者の操作が必要なため)

## Risks / Trade-offs

- **ACK を返さない旧サイネージと接続すると必ずタイムアウト警告が出る** → リモコンとサイネージは同一デプロイから配信されるため実運用では同一バージョンになる。混在は開発時のみで、その場合も再送で復旧できる
- **単一送信に絞るため、エントリーの連続記録でテンポが落ちる** → ラウンドトリップは通常 300ms 未満で、オーバーレイの視覚表示も出ない。実機で違和感が出た場合は「クイック追加だけ送信中表示を省く」などの調整余地を残す
- **メッセージ数が約 2 倍になる(コマンド 1 件につき ACK 1 件)** → 1 トーナメントあたりの操作回数は多くても数百件で、Ably の無料枠に対して無視できる
- **ネットワークが遅い環境で 5 秒タイムアウト後に ACK が届く** → 遅れて届いた ACK は「送信済み」として扱い、失敗警告を成功表示へ差し替える。利用者が再送してしまっても `requestId` の重複排除で二重適用にはならない
