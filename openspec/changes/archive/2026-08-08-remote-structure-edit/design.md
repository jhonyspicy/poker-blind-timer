# remote-structure-edit: 設計

## Context

- ストラクチャーは `TournamentConfig.structure`(`StructureItem[]`)としてサイネージ側 PC の IndexedDB にのみ存在する。リモコン(スマホ)は別デバイスで、状態スナップショット経由でしか状態を知らない
- タイマーは `TimerState.levelIndex` でストラクチャー内の位置を指す。`resolveTimer` は純関数で、基準時刻と各項目の持ち時間から現在位置を導出する
- リモコンのコマンドは「操作意図」を送り、適用結果はサイネージが決定する(`requestId` による重複排除つき)。セッションの変更は既存の仕組みで自動的に IndexedDB へ保存され、スナップショットが配信される
- エディタのストラクチャー検証は `validateConfig`(`src/domain/config.ts`)にある

## Goals / Non-Goals

**Goals:**

- リモコンから未来のストラクチャー項目を編集できるようにする
- 編集はセッション限定の上書きとし、保存済み設定(configs ストア)を変更しない
- タイマーの正確性・レベル進行の整合性を一切損なわない
- リロード後も上書きが復元される

**Non-Goals:**

- 進行中・過去の項目(通過済みのブレイク・レイトレジ締切マーカー含む)の編集
- 上書き内容の保存済み設定への書き戻し(将来「テンプレートに保存」を足す余地は残す)
- エディタ(`/editor`)側の変更
- 進行中レベルの残り時間変更(既存の `SET_REMAINING` で対応済み)

## Decisions

### D1: 上書きは `SessionState.structureOverride` に全量で持つ

`SessionState` に `structureOverride?: StructureItem[]` を追加し、適用後のストラクチャー全体を保持する。実効ストラクチャーは `structureOverride ?? config.structure`。

- 差分(パッチ)形式より単純で、リロード復元時に config との突き合わせが不要
- 旧セッションデータはフィールドなし = 上書きなしとして自然に扱え、DB スキーマバージョン更新は不要(session ストアは keyPath なしの単一キー保存)
- サイネージ内部では「実効 config」(`structure` を差し替えた `TournamentConfig`)を 1 箇所で導出し、タイマー進行・スナップショット生成・画面描画のすべてでそれを使う。下流のコードパスは既存のまま変えない

### D2: コマンドはストラクチャー全量を送り、サイネージがプレフィックス一致で検証する

`STRUCTURE_UPDATE { requestId, structure: StructureItem[] }` を追加する。適用時、サイネージは:

1. `resolveTimer` で現在位置を解決する(`waiting` なら制約なし、`finished` なら拒否)
2. 受信した `structure` の先頭 `[0..現在 levelIndex]` が実効ストラクチャーの同区間と項目単位で一致することを検証する(進行中・過去の改変を拒否)
3. ストラクチャー検証ルール(ブラインド 1 つ以上、レイトレジ締切 1 つまで、継続時間 > 0、SB/BB > 0、Ante ≥ 0)を満たすことを検証する
4. すべて通れば `structureOverride` に採用してセッションを保存する

「未来のみ編集可」を index 指定(`fromIndex` + 差し替え項目)で表現する案もあるが、全量+プレフィックス一致の方が競合検出を兼ねられる: リモコンが編集している間にレベルが自動遷移した場合、遷移後の現在項目に触れる編集はプレフィックス不一致で自動的に拒否され、触れない編集はそのまま適用できる。境界の判定は必ず**適用時点のサイネージの解決結果**で行う(リモコン側の表示は古い可能性があるため)。

### D3: 拒否は再同期で伝える(専用 NACK メッセージは作らない)

検証に失敗した場合、サイネージはセッションを変更せず、現在の状態スナップショットを配信し直す。リモコンは `STRUCTURE_UPDATE` 送信後の次のスナップショットで結果を判定する:

- 受信したストラクチャーが送信内容と一致 → 適用成功として編集画面を閉じる
- 一致しない → 「タイマーの進行と競合した」旨を表示し、受信した最新ストラクチャーで編集画面を更新する

メッセージ種別を増やさず、既存の「サイネージが正・スナップショットで回復」の設計と揃える。

### D4: スナップショットに実効ストラクチャーと現在位置を追加する

`StateSnapshot` に以下を追加する:

- `structure: StructureItem[]` — 実効ストラクチャー(上書き適用後)
- `currentIndex: number | null` — 解決済みの現在項目 index。`waiting` / `finished` は null

リモコンはこれで編集画面(過去・現在ロック、未来編集可)を構成する。ストラクチャーは高々数十項目なので Ably のメッセージサイズ制限には十分収まる。

### D5: 検証ロジックは `validateStructure` として domain に切り出す

`validateConfig` のストラクチャー部分を `validateStructure(structure: StructureItem[]): string[]` に抽出し、エディタ(既存の `validateConfig` 経由)・サイネージ(適用時の権威的検証)・リモコン(送信前の即時フィードバック)で共用する。

### D6: リモコンの編集はドラフト方式+適用確認

編集画面ではローカルのドラフトを操作し、「適用」ボタン+確認ダイアログで初めて `STRUCTURE_UPDATE` を送信する(誤タップによる意図しない構造変更を防ぐ)。編集可能な操作:

- 未来のブラインド項目の SB / BB / Ante / 継続時間の変更
- 未来のブレイク項目の継続時間の変更
- 未来位置への項目追加(ブラインド / ブレイク / レイトレジ締切=未設置の場合のみ)と未来項目の削除
- 進行中・過去の項目は表示のみ(現在項目を明示する)。`waiting` 中は全項目が編集可

## Risks / Trade-offs

- [編集適用の瞬間にレベルが自動遷移する競合] → D2 のプレフィックス一致検証で、遷移後の現在項目に触れる編集は適用されない。リモコンには D3 の再同期で競合を通知し、最新状態から編集し直せる
- [未来のレイトレジ締切マーカーの削除・移動で優勝確定条件が変わる] → 未到達のマーカーは編集対象として許可する。削除するとフリーズアウト扱い(現在人数だけでインマネ等が確定)になり、既存の締切到達検知(`justClosed`)がその時点で発火する。これは「締切を今なくす」という運営判断そのものなので仕様どおりの挙動とするが、リモコンの削除確認でその旨を警告する
- [上書き後に最後の項目まで消化した場合の finished 遷移] → プレフィックス一致により現在項目は必ず残るため、`resolveTimer` の終端処理は既存のまま安全
- [スナップショット肥大化] → ストラクチャーは数十項目程度で、配信頻度もセッション変更時のみ。実害なし
- [リモコンとエディタの編集 UI 重複] → スマホ向けに簡素な UI を新規に作る(エディタの流用はしない)。表示ロジックの重複は許容し、検証だけ D5 で共用する
