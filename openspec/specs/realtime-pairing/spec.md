# realtime-pairing: 接続 URL 発行・トークン認証・ペアリング

## Purpose

接続用 URL の発行・Ably トークン認証・QR ペアリング・リアルタイムメッセージ同期の基盤を定める。
## Requirements
### Requirement: 接続用チャンネル ID の発行
Cloudflare Worker は、サイネージからの要求(`POST /session`)に対し、暗号学的に推測困難なランダムなチャンネル識別子(128bit 以上)を発行しなければならない(MUST)。

#### Scenario: チャンネル ID の発行
- **WHEN** サイネージが `POST /session` を呼び出す
- **THEN** 一意で推測困難なチャンネル識別子が返される

### Requirement: Ably トークン認証
Cloudflare Worker は、トークンエンドポイント(`GET /token?ch=<id>`)で、指定チャンネルに capability を限定した Ably の TokenRequest を返さなければならない(MUST)。Ably の API キーは Worker の環境変数(secret)のみに保持し、フロントエンドのコード・ビルド成果物に含めてはならない(MUST NOT)。

#### Scenario: トークンの取得
- **WHEN** サイネージまたはリモコンがチャンネル識別子つきでトークンエンドポイントを呼び出す
- **THEN** そのチャンネルに限定された TokenRequest が返され、Ably へ接続できる

#### Scenario: API キーの秘匿
- **WHEN** フロントエンドのビルド成果物を検査する
- **THEN** Ably の API キーは含まれていない

### Requirement: 開始モーダルでのペアリング
トップページで「開始」または「再開」を押すと、ペアリング用のモーダルを表示しなければならない(MUST)。モーダルは次の順で進行する:

1. 「少々お待ちください」を表示し、Worker からチャンネル ID を取得して Ably へ接続する
2. 接続が完了したら、チャンネル識別子を含むリモコン用 URL(`/remote?ch=<id>`)を QR コードとその下の URL リンク(新しいタブで開く)で表示し、「操作端末で開いてください」と案内する
3. リモコンの接続を検知したら「ブラインドタイマーを開く」ボタンを表示する
4. ボタンを押すとサイネージ画面へ遷移し、フルスクリーン表示にする

リモコンの接続検知には Ably の presence を使用する(リモコンが入室を宣言し、サイネージ側が検知する)(MUST)。

#### Scenario: 開始からサイネージ表示まで
- **WHEN** トップページで設定の「開始」を押し、表示された QR コードをスマホで読み取ってリモコンを開く
- **THEN** モーダルに「ブラインドタイマーを開く」が表示され、押すとサイネージ画面がフルスクリーンで開く

#### Scenario: 接続待ちの表示
- **WHEN** チャンネル発行直後でリモコンが未接続である
- **THEN** QR コードと URL、「操作端末で開いてください」の案内が表示されている

### Requirement: サイネージからの QR 再表示
サイネージは、リモコンが使用不能になった場合に備え、タイマー表示中にも同じチャンネルの QR コードを再表示できなければならない(MUST)。

#### Scenario: タイマー表示中の再表示
- **WHEN** タイマー表示中に QR コードの再表示を操作する
- **THEN** 同じリモコン用 URL の QR コードが表示され、別の端末から接続し直せる

### Requirement: リアルタイムメッセージ同期
サイネージとリモコンは同一の Ably チャンネルに接続し、リモコンの操作コマンドがサイネージへ、サイネージの状態スナップショットがリモコンへ配信されなければならない(MUST)。通信が切断されてもサイネージのタイマー進行は継続し(MUST)、再接続後に同期が回復しなければならない(MUST)。

サイネージは、受信したリモコンコマンドを処理した時点で、そのコマンドの `requestId` と受理結果を含む確認応答(ACK)をチャンネルへ配信しなければならない(MUST)。ACK の受理結果は次のいずれかとする:

- `accepted`: コマンドを受理した。処理済み `requestId` の再送(重複排除で適用をスキップした場合)も `accepted` を返さなければならない(MUST)
- `rejected`: 優勝確定後などでコマンドを受け付けない状態だった

サイネージはコマンドの種別や適用結果にかかわらず、受信したすべてのコマンドに対して ACK を返さなければならない(MUST。返さない経路があるとリモコン側で送信失敗と誤判定されるため)。

#### Scenario: コマンドの配信
- **WHEN** リモコンがコマンドを publish する
- **THEN** サイネージが subscribe でそのコマンドを受信する

#### Scenario: コマンドの確認応答
- **WHEN** サイネージがリモコンのコマンドを受信して処理する
- **THEN** そのコマンドの `requestId` と `accepted` を含む ACK がチャンネルへ配信され、リモコンが受信する

#### Scenario: 受け付けない状態でのコマンド
- **WHEN** 優勝が確定した後にリモコンからのコマンドがサイネージへ届く
- **THEN** コマンドは適用されず、`rejected` の ACK が配信される

#### Scenario: 同一 requestId の再送
- **WHEN** ACK が届かず、リモコンが同じ `requestId` でコマンドを再送する
- **THEN** サイネージは重複排除により再適用せず、`accepted` の ACK を返す

#### Scenario: 切断中のタイマー継続
- **WHEN** サイネージのネットワークが一時的に切断される
- **THEN** タイマーはローカルで正しく進行し続け、再接続後にリモコンとの同期が回復する
